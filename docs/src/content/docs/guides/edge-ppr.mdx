---
title: Edge PPR
description: Serve PPR static shells from your CDN's edge while the compiled binary renders only the dynamic holes — no KV, no push pipeline, no per-release steps.
---

Partial Prerendering splits a page into a build-frozen static shell and
per-request dynamic holes. Compiled binaries handle PPR **origin-only out
of the box**: the shell flushes immediately (TTFB never waits on data)
and the holes stream into the same response. Nothing on this page is
required for PPR to work.

What this guide adds is the CDN half of Next's
[PPR platform protocol](https://nextjs.org/docs/app/guides/ppr-platform-guide):
serving the shell from the edge (~10–30ms first paint, asset preloads
starting immediately) while your origin renders only the holes. In a
real deployment this took a warm dashboard hard-load from ~350ms of
blank tab to a 23ms first byte.

**Do you need this?** Only for routes that mix a static frame with
per-request content *and* whose first paint matters. Fully static pages
get the same edge TTFB from a plain CDN cache rule with zero moving
parts. The holes render at origin speed either way.

Two ways to reach the shells, both off by default:

- **The edge contract (v2, `EDGE_TOKEN`)**, a framework-neutral protocol
  that also hands the edge fully static pages to serve whole. Use it for
  a platform, or for the example Cloudflare worker.
- **The `/_nbc/ppr-shell` endpoint (`NBC_PPR_SHELL`)**, the original
  next-bun-compile protocol, for edge integrations built against it. It
  is maintained alongside the contract.

:::caution[v3: the PPR contract (v1) is gone]
v2.1's `ppr.json`, `/_ppr/shell`, `/_ppr/resume`, `PPR_TOKEN`,
`PPR-Token` and `PPR-Build` are replaced by the edge contract, with no
compatibility layer. Set `EDGE_TOKEN` instead of `PPR_TOKEN` and send it
as `Edge-Token`; read `edge.json`; fetch `/_edge/page?path=<path>`
(which also answers static pages, with `complete: true`); resume with
`POST /_edge/resume`, and match `Edge-Build`. A build deletes any
`ppr.json` it finds beside its own marker.
:::

## How it fits together

1. **The edge contract (opt-in, `EDGE_TOKEN`).** The binary serves each
   PPR page's build-frozen shell and its postponed state, renders only
   the holes when handed that state back, and serves fully static pages
   whole:

   ```
   GET  /_edge/page?path=<path>         →  { v, build, html, state, complete?, headers? }
   POST /_edge/resume?url=<path+query>  →  the holes only
   ```

   Pages are discovered at boot from the extracted tree and served from
   memory — request data never touches the filesystem. Every one comes
   from a prerender — at build time, or a later regeneration — never from
   the context of a visitor's request, so none can contain per-user data.
2. **An edge worker (yours, or the example).** Caches the page, streams
   it instantly, and for a shell resumes the holes from your origin and
   stitches one response. A complete self-populating Cloudflare
   implementation ships in
   [`examples/cloudflare-edge-worker`](https://github.com/ramonmalcolm10/next-bun-compile/tree/main/examples/cloudflare-edge-worker).

## The edge contract

A platform that runs the build can skip discovery entirely. Every build
speaks the edge contract (v2), a framework-neutral protocol between a
framework and an edge: one marker, one page endpoint, one resume
endpoint, one build header. An edge that implements it serves any
framework that does, with no per-framework code.

**The marker.** Every build writes `edge.json` to `.output/edge.json` in
the project, where the contract has a builder look for it, and next to
the binary (`dist/` by default), so it ships with the binary. With
`NBC_OUT=.output` the two are one file. Both lists are `[]` when no page
qualifies, and the build says why (basePath or i18n set, or a proxy that
runs on every page, named):

```json
{
  "v": 2,
  "build": "Q6p5InH-AoAKW6ZLAyNXg.3f9c0a1b2d4e",
  "shells": ["/pricing", "/blog/hello-world"],
  "static": ["/", "/about"],
  "bypass": {
    "headers": ["RSC", "Next-Router-Prefetch", "Next-Router-Segment-Prefetch", "Next-Router-State-Tree", "Next-Action"],
    "query": ["_rsc"],
    "cookies": ["__prerender_bypass"]
  }
}
```

- `shells` lists PPR pages; `static` lists pages Next froze whole for
  the build. No path is in both. Paths are decoded (`/über`, not
  `/%C3%BCber`) and in the form the app serves them, following
  `trailingSlash`. Both lists come from the same selection the endpoint
  runs at boot, so the endpoint refuses exactly what they leave out:
  pages a proxy or a routing rule covers, fallback shells, paths a
  client can't send unchanged, and anything past the limits (200 paths
  of at most 200 bytes per list, shallowest kept, with a build warning
  naming the rest).
- `static` also leaves out pages with a revalidate timer, a status other
  than 200, error pages, and pages whose response headers an edge may
  not send (below).
- `build` is `BUILD_ID` plus a digest of every listed page — each static
  page's HTML, each shell and its state, and their headers
  (`Q6p5InH-AoAKW6ZLAyNXg.3f9c0a1b2d4e`), so it changes whenever a stored
  page does. That matters with a custom `generateBuildId`: one that
  returns the git SHA keeps its id when the same commit is rebuilt with
  new build-time data (a CMS publish, a changed env var). The build
  stamps the value into the binary, so `Edge-Build` always matches the
  marker. An id outside `[A-Za-z0-9._-]`, or too long to carry the
  digest, becomes the digest alone.
- `bypass` names Next's own requests on a page's path (client
  navigations, prefetches, actions, draft mode), which an edge passes to
  the origin untouched.

**Headers.** A page goes out with only the headers on the contract's
list, fixed for the build: `content-language`, `link`, `cache-control`,
`x-robots-tag`, the security headers (`content-security-policy`,
`permissions-policy`, `referrer-policy`, `strict-transport-security`,
`x-frame-options`, `x-content-type-options`, the three `cross-origin-*`
policies) and `x-dns-prefetch-control`, at most 16. A `headers()` rule in
`next.config` that sets only listed headers, unconditionally, travels
with the page as `headers`. One that sets any other header, has a
`has`/`missing` condition, or builds a value from the path keeps every
page it covers at the origin.

**The endpoints.** With `EDGE_TOKEN` set, and the same value in an
`Edge-Token` header:

```
GET  /_edge/page?path=<decoded path>    →  { v, build, html, state, complete?, headers? }  + Edge-Build, ETag
POST /_edge/resume?url=<path and query> →  the holes only (text/html)  + Edge-Build
```

- A static page answers with `state: ""` and `complete: true`: serve
  `html` as the whole document. It has no resume.
- The resume's body is the shell's `state`, raw. The binary re-sends it
  to Next as its own form-encoded `next-resume` POST with the visitor's
  headers, cookies and query, so a hole that reads `searchParams` sees
  the visitor's. The response is never compressed, and never starts a
  second document: one that would is refused with a 502.
- The page answers `If-None-Match` with a 304, since ISR or a
  revalidated tag can change a shell within a build. A static page that
  `revalidatePath` or `revalidateTag` touches is re-rendered through
  Next from then on; if that render isn't a plain 200 HTML page, the
  endpoint 404s it.
- Every answer under `/_edge/`, a 404 included, is
  `Cache-Control: private, no-store`. They are answered only for the
  token, so no cache between the edge and the origin may keep one.
- Without `EDGE_TOKEN`, or with a missing or wrong header, everything
  under `/_edge/` is a 404, so the endpoints are invisible wherever the
  binary runs.

The binary runs the contract's conformance script in its regression
suite (`test/regression/edge-conformance.mjs`, kept in step with
rsc-kit's). It checks, among the rest, that a static page is byte for
byte the page the origin serves and that every asset it links is
immutable. Run it against your own deployment with
`EDGE_TOKEN=… node test/regression/edge-conformance.mjs <dir with edge.json> <base url>`.

## The /_nbc/ppr-shell endpoint

`NBC_PPR_SHELL` serves the same shells in next-bun-compile's own shape,
`GET /_nbc/ppr-shell/<route>` → `{ shell, postponed, buildId, tags }`,
resumed with a `next-resume` POST to the page itself. It is independent
of the edge contract; either, both or neither may be on.

```bash
NBC_PPR_SHELL=1 ./dist/app            # open mode
NBC_PPR_SHELL=some-shared-token ./dist/app   # token mode
```

- **Open mode** responses are `Cache-Control: public, max-age=3600` —
  build-time content that shared caches may hold.
- **Token mode** requires the value in an `x-nbc-shell-token` header
  (401 otherwise) and responds `private, no-store`. Use token mode for
  auth-gated routes so their skeletons aren't publicly enumerable —
  and note the header is load-bearing: behind a zone-wide "cache
  everything" CDN rule, a publicly-cacheable tokened response would be
  cached once and served to anyone, silently defeating the token.
- Routes without a PPR pair (fully static, or fully dynamic) return
  404. Unset the variable and the endpoint doesn't exist.
- Fallback shells (`/docs/[slug]` with no prerendered match) return
  404 too. Outside Next's minimal mode, a resume for a path that wasn't
  prerendered renders the whole document and ignores the postponed
  state, so an edge would append a second document to the shell. Only
  concrete prerendered paths, including a dynamic route's
  `generateStaticParams` output, have shells.

## The Cloudflare worker

The example worker needs **no KV, no build-time push pipeline, and no
CI changes**:

- **Cache miss** → the visitor passes through to the origin while the
  page warms into `caches.default` in the background. No request is
  ever slower than having no worker.
- **Cache hit** → a static page is served whole from the edge. A
  shell streams from the edge; in parallel a resume `POST` renders the
  holes at the origin and pipes onto the same response.
- **Build skew or resume failure** → the holes are appended only when
  the resume's `Edge-Build` matches the cached shell's build. Otherwise
  the cached shell is evicted and that visitor keeps the shell's
  Suspense fallbacks — degraded, never mixed builds.

Deploy once, ever:

```bash
cd examples/cloudflare-edge-worker
# set your route pattern(s) in wrangler.toml
wrangler secret put EDGE_TOKEN      # the value the origin runs with
wrangler deploy
```

One deployment serves every app in your account — the shell cache key
derives from each request's hostname, so apps never mix. Attach route
patterns narrowly (only paths in `edge.json`): everything else should never invoke
the worker.

### Staleness

- **Deploys:** the build check above carries the edge across a deploy
  on its own: a shell from the old build is evicted on its first hit and
  re-warmed from the new one. A static page has no resume to carry the
  build, so it is replaced by the background re-check below, within
  about a minute; purge on deploy to make that immediate. A purge-on-deploy job (zone
  `purge_everything`) spares that one degraded load, but nothing depends
  on it.
- **Runtime revalidation:** the endpoint entry is never dropped. It reads
  the route's pair back through Next's own incremental cache — the same
  source Next serves from — and falls back to the prerender on disk. A
  shell that regenerates (an ISR expiry, or a `use cache` region inside
  it whose tag was revalidated) therefore follows the origin wherever the
  configured handler put it: on disk, in a memory tier, or in the shared
  store a custom `cacheHandler` writes — including on a pod that only
  ever reads what a different pod regenerated. A shell that never
  regenerates (a static frame around dynamic holes) keeps its
  build-frozen pair: the postponed state is code-shaped, only a new build
  changes it, and that is a new process which re-reads at boot.
- **Before the first render there is nothing to read back.** An endpoint
  request that arrives before the binary has booted Next serves the build
  output; it self-corrects as soon as the process handles a request.
- **The edge copy converges on its own.** An origin cannot evict a CDN's
  copy, so the example worker revalidates instead: on a warm hit older
  than a minute it re-checks `/_edge/page` in the background with
  `If-None-Match`. An unchanged shell answers `304` with no body; a
  regenerated one replaces the cached copy. The edge therefore follows a
  regeneration within about a minute instead of sitting stale for the
  rest of its hour, at the cost of one bodiless request per PoP per
  minute.

## Hard-won details

The example worker already handles these; they're documented so you
don't rediscover them in an integration of your own:

- **Every pass-through must bypass the zone cache**
  (`fetch(req, { cache: "no-store" })`). A worker subrequest is *not*
  automatically the no-worker behavior: it transits Cloudflare's cache,
  which keys on URL alone and ignores `Vary` — and Next serves a PPR
  route's segment-prefetch payloads with `s-maxage=31536000` at the
  same URL as its document. Without the bypass, one passed-through
  prefetch caches flight data under the document's URL and every
  document load on that route returns raw RSC until the zone is
  purged. The symptom is a page rendering as `text/x-component`
  protocol text right after a deploy (the purge empties the cache and
  the refill race begins).
- **Resuming against the page needs a form content type.** This only
  matters if you skip `/_edge/resume`, which handles it for you. A
  `next-resume` POST to the page must be
  `application/x-www-form-urlencoded`: Workers' `fetch()` stamps string
  bodies `text/plain` (or `application/octet-stream`), and Next rejects
  those with 405 *before* its resume branch. The symptom is an
  intermittent stuck-on-fallbacks page as the cache self-evicts and
  re-warms.
- **Ask for the resume uncompressed.** The worker's response is
  compressed whole by Cloudflare, so the holes must arrive as plain
  bytes to append to the shell. The example drops the visitor's
  `Accept-Encoding` from the resume, and `/_edge/resume` never
  compresses anyway.
- **Never key the cache on a URL you also fetch.** A cache key is an
  identifier, not a fetch target, and `caches.default` *is* the zone
  cache — so keying on `/_edge/page?path=<path>` inherits whatever
  cacheability that URL has picked up, including from the worker's own
  `cache: "no-store"` shell fetch. Telling Cloudflare never to cache a
  URL and then asking it to cache that URL loses: `put()` resolves
  normally and stores nothing, so the shell re-warms on every request
  and is never served, with no error raised anywhere. The example keys
  on a synthetic `/__edge-page/<path>` instead, judged only on the
  response it is handed. A declined `put()` does not throw, so reading
  the key straight back is the only way to tell a real write from a
  discarded one — worth doing once when bringing up an integration.
- **A freshness check must bypass the zone cache too.** A worker
  subrequest that transits the zone can be answered with the very copy
  you are trying to replace — the check validates against itself and
  never sees the new shell. `/_edge/page` answers `private, no-store`,
  but a zone-wide "cache everything" rule can override that, so the
  example fetches it with `cache: "no-store"` regardless.
- **Forward the original request headers on the resume** — the
  holes are per-user and the origin needs cookies to render them. They
  flow only worker → origin (the path they already travel); nothing
  user-specific is ever cached, and the combined response is
  `private, no-store`.
- **Only document GETs take the shell path.** The marker's `bypass`
  list (RSC, prefetches, server actions, draft mode), other methods, and
  non-HTML `Accept` headers pass through — the
  client router's own requests never hit the worker's logic.
- **Auth-gated routes change redirect UX.** The worker serves the
  (public, build-time) shell before your auth can 302, so logged-out
  visitors get the shell and are redirected client-side after
  hydration instead of instantly. Decide per route whether that's
  acceptable.
- **Edge shells only apply to document loads** — first visits,
  reloads, direct links. Client-side navigations fetch RSC payloads
  and never make document requests.

## Verifying

```bash
# the contract is invisible without the token
curl -s -o /dev/null -w '%{http_code}\n' 'https://your-app.com/_edge/page?path=/route'   # 404
# warm document: edge shell + streamed holes
curl -s -D- -o /dev/null -H 'Accept: text/html' https://your-app.com/route \
  | grep x-edge-build
```

In the browser: hard-reload the route twice with DevTools open. The
warm load's document shows `x-edge-build`, first byte in tens of
milliseconds, and the full response streaming in behind it. For live
worker telemetry, `wrangler tail` — the example logs failed warms and
resumes it didn't append.
